# 兵营容量与奖励保留

本轮只做后台实现和定向验证。原生依据为 `aigis_research/permanent-20261101/unit-capacity-contract.md`，没有启动游戏或重启正式服务。

## 容量计算

`UnitCapacity` 使用服务启动时固定的公共主表与资源。第一兵营容量为：

```text
198 + AppendOfFirstBarrakcsCapacity
    + floor(min(Rank, 200) / 10)
    + 2 * floor((min(Type1已通关数, ClearQuestCountLimit) + 5) / 10)
    + 4 * 已通关的1108/1208/1306数量
```

公式常数在 `unit_capacity` 中具名：198为 `FIRST_BARRACKS_BASE`，200为 `RANK_LIMIT`，每十级与每十次通关的10分别为 `RANK_STEP` 与 `CLEAR_STEP`（+5为 `CLEAR_STEP // 2`），2为 `CLEAR_BONUS`，4为 `SPECIAL_QUEST_BONUS`，1108/1208/1306为 `SPECIAL_QUESTS`；ClearQuestCountLimit取自OnCommand键 `CLEAR_LIMIT_COMMAND`（0x724270C7）。启动时用同一公式在Rank 200、全部计数关卡（不按上限截断）与三个特别关卡都通关时求上界，核对它在int32内。

只认 `AchieveFlag & 0x01000000`，不把剧情已读、星级或掉落收集当作通关。当前追加值558、通关计数上限55，第一兵营容量756至800；额外兵营容量900。缺少可选设置时使用原生默认：追加0、额外容量250、通关计数不截断。动态或无法识别的相关命令明确报错，不执行任意脚本。

`HaveUnitMaxSizeBuy` 高16位（`barracks_service.EXTRA_SHIFT`）表示额外兵营数量，当前最多两座（`MAXIMUM_EXTRA_BARRACKS`）；低16位旧购买次数不增加当前公式。普通角色按 `GeneralPurposeFlags` 第4至7位分组计数，锁定、编队、圣灵和王子的真实行都计数；PSH/PFF/PPT不占普通兵营名额。旧的超容量存档不截断，41仍能读出；无法解释的兵营索引不会被当成免费空间。

## 各操作的处理

| 操作 | 容量不足时 |
|---|---|
| 1/2单领 | 保留整次所选邮件及资产 |
| 117批领 | 按请求顺序领取能完整放下的邮件；跳过放不下的整份奖励，后面的较小奖励仍可领取 |
| 125圣灵取出 | 本次整批都要放得下，否则库存不扣 |
| 128银仓取出 | 要有一个名额，否则库存不扣 |
| 127银仓存入返还 | 分开检查第一兵营净增加与删除源实例后的技术容量；旧超限但净减少或持平可继续 |
| 77/81开战 | 第一兵营至少有一个空位，且本场潜在角色奖励能通过技术容量预检 |
| 80/83结算 | 正常发放本场合法角色奖励，允许暂时超过兵营玩法上限；下一次开战重新检查 |

117的选择顺序由用户确认，是本地策略。已有结晶超上限时不删除或截断余额；放不下的邮件继续保留。批领响应重试使用持久回执，不会重复发奖。容量全满导致一封也没领到的117不写回执，重发时按当前状态重算，同样不会重复发奖。客户端使用42重新读取后可发现尚未领走的邮件。

## 存储边界与进行中的战斗

4096行、int32唯一编号及完整41响应大小是独立的技术边界。`credit_units` 保持为候选存档的发卡原语，外层业务入口检查相应兵营限制；不能用严格兵营上限阻断已完成战斗的奖励。

进行中的战斗在 `quest_state.active.unit_reservations` 保存潜在角色奖励清单，不写入当前持有角色。其他发卡先试算“本次发卡后，再发完预留奖励”，预检行数、编号和41响应，实际只保存本次操作。结算候选状态释放自身预留后发奖，退出或重开则随旧场次释放。存档提交仍使用同次CAS，冲突后重新计算。

旧场次没有预留清单时仍可结算、退出或重开；在此之前暂缓其他发卡操作，读取、货币领取及不发新角色的整理不受这条限制。没有迁移或修改正式存档。

## 控制台

控制台向名册加入新实例的命令复用同一容量计算：`units.grant`、`fame.withdraw`、`silver.withdraw`和`fairy.withdraw`照常检查兵营业务空位，units域的预检再按技术上限试算进行中战斗的奖励预留。不提供强制超容量编辑（已决定不实现，与控制台「不提供force」同一取向）：任何把名册推过容量的入口都不存在，普通游戏请求也不绕过。

额外兵营购买17与转移118已接入，见`barracks-flow.md`；本模块负责正确识别已有分组并防止计数错误。原生界面、满仓提示和断线回读仍待用户要求实机后验收。
