# 通行证自动补领

新的116登录奖励请求会检查已结束通行证，将已有EP能领取的未领档位自动投递到邮箱。它与159手动领奖共用`event_pass_state`和两轨已领点位，不重复发奖，不扣EP，也不自动授予高级资格。

## 明确的本地结束规则

自动结算默认开启。满足以下任一条件才检查该通行证：客户端整秒时钟（服务端时刻先落到客户端4 ms网格的整秒）晚于EndDate，即EndDate当秒过后的下一秒起；或者这个时钟已到StartDate且Status在`closed_statuses`中。默认列表为`[2]`，对应当前快照中不再开放手动领奖的六组通行证。这个列表是本地政策，不宣称Status2就是已还原的官方结束调度。TimeLimit始终只保留为显示文本。

`--event-pass-rules`及启动脚本参数`-EventPassRulesFile`可加载规则，示例见`config/event-pass-rules.example.json`。`closed_statuses: []`表示只按EndDate，`enabled: false`关闭自动投递；显式列表不追加默认值。规则在构造服务时冻结并参与自动领取指纹，修改后需要重建服务。

本功能在新的116请求中执行，没有另起定时服务，离线时不写存档。没有已获得EP、没有高级资格或所有合格奖励已经领取时，不创建奖励邮件。

## 原子性和待处理记录

每个通行证的全部新合格档位仍须完整入箱后才推进水位。邮箱容量、暂不支持的奖励或回复容量不足时，该通行证保留原进度，在`event_pass_automation.pending`记录原因；其他能够投递的通行证和等级奖励可以继续。后续新的116请求再次检查，成功或已无待领奖励后清除对应原因。奖励物品名超过255字节原生单元时按501 `event_pass_reward_unsupported`记为待处理，不让邮件写入方的503中止整次116。通行证ID超过255字节原生单元、无法新建状态行时同样不中止，以`event_pass_identity_unreplayable`记为待处理并记一条WARNING。普通或高级物品身份变化后，已有投递记录的通行证再补领时以`event_pass_definition_changed`记为待处理，每次检查都记一条WARNING，点名控制台命令`event_pass.rebind_definition`；不中止整次116，其他通行证和等级奖励照常投递。改绑之后，下一次116按当前定义补领原生水位以上的档位，并清除该原因。

无效存档、损坏状态源等错误仍中止整次事务。新增邮件、A9分类、两轨水位、等级奖励、待处理原因和116回执在同一次CAS中提交；并发重读共享水位，因此自动与手动领取不会各发一份。

## 邮件与旧回执

自动投递的邮件保存可选`NotificationCategory=7`，对应PPT.A9:I。奖励Type、数量和身份保持原本含义。旧邮件不补写分类；只有选中的返回行存在显式分类时才输出整列A9，其余行填0，保留旧响应形状。

116的`rank_reward_history`为schema2，旧版schema1读取时自动升级。旧`rank_reward_delivery`版本1与原有纯等级内容指纹继续支持；新混合投递使用版本2，分别记录`rank_mail_ids`和按通行证分组的`event_pass_mail_ids`。两类来源不重叠，合并后必须等于响应邮件列表。通行证ID按字典序排列，重开存档后回包顺序一致。

旧纯等级回执的精确重放不调用自动结算或时钟。新混合回执同时验证自动规则、完整存档、实际来源、PPT和137中的领奖状态；缓存不会重新投递或借重算摘要绕过待处理状态校验。自动领取指纹由`automation_content_version_for`按道具定义的版本求值，称号目录在回执提交之后才接入时，旧116回执照常重放，见`rank-rewards.md`。`automation_content_version_for`同时接受通行证目录版本：按JST时刻比较窗口时提交的116回执，其自动领取指纹按旧规则名`status_1_and_inclusive_start_end_jst`的目录版本求值，旧回执照常精确重放；伪造的摘要仍回409 `rank_reward_retry_stale`。升级结算仍只调用原有等级奖励`apply`，不在战斗路径自动补领过期通行证。

## 提示生命周期与剩余范围

原生116扫描新到达且A9=7的邮件，集中提示后清除客户端的运行时新到达位。随后42全量读取会清所有新到达位，保留分类与邮件。服务端不制造或保存这个内部位。若旧增量回包在冷进程的空邮箱中首先到达，仍可能重复显示提示；发奖去重独立于提示次数，不因此再发奖励。

原生依据见`aigis_research/events-20261101/event-pass-auto-contract.md`。本轮只做后台实现和定向验证；原生弹窗未实测。期间限定任务的EP来源、高级资格购买和客户端复刻目录仍需继续接通。

## 验证与批量性能

239项相关测试的最终结果通过，见`artifacts/event-pass-auto-verified-tests.xml`与`event-pass-auto-validation.json`。覆盖A9旧数据兼容、结束规则、待处理恢复、116混合来源回执、手动/自动防重、缓存状态校验、实际邮件领取、原子回滚和批量构建；未运行全项目测试。

批量性能调查定位到逐张票重复校验静态资源，以及逐积分档重复扫描整个邮箱。邮箱扫描现在捕获同一份只读票据目录，首尾验证依赖，每封仍独立校验字段；不跨请求缓存校验结果。`enqueue_groups`复用同一套奖励转换逻辑，一次准备同一通行证的所有分组，再统一分配邮件ID和编码，保留各档对应的发件清单。旧`enqueue`使用单组包装。

同样6组、264封、21,365字节回复的单次新116请求，cProfile对照从78.44秒降至4.27秒；独立无分析器测量为2.38秒。邮箱扫描次数由433降至45，按档入箱200次改为按通行证6批，提交仍只有一次。测量不含服务构造、客户端网络和画面渲染，不是实机延迟保证。原始与两轮修改后的统计均保留，见`artifacts/event-pass-auto-profile.batch.md`与`.raw.json`。

只读`event-pass-auto-doctor.json`确认组件和启动依赖就绪；实际数据库仍为12,288字节，修改时间2026-11-01 06:45:52。启动脚本新增规则参数已做语法校验，本轮没有启动游戏或生产服务。
