# 购买后每日领奖礼包

本地日奖礼包已接入46/47目录、50免费购买资格及115/116每日领奖。它使用原生PackageItemType10和LoginBonusID，不用虚构库存物品代表资格。与高级通行证礼包共用商店入口，但存档和奖励来源独立。

## 开启与资源

默认不出售。通过`--purchased-login-rules`或PowerShell的`-PurchasedLoginRulesFile`加载`config/purchased-login-rules.example.json`开启。独立客户端准备程序接受同名参数，必须与服务端使用相同的配置以取得匹配文案和资源版本。

- `enabled`控制出售。关闭后，已经取得的资格仍按原条件发奖。
- `campaign_ids`可选择已有Type2活动；`null`选择当前全部16组。
- `purchase_limit`默认1，按活动累计购买次数。提高上限可再次取得资格，但当前同活动仍有效或有待发奖励时不能叠加购买。

这些是明确的本地免费商品，不冒充未采集的官服SKU、价格或销售安排。16组共有168条日奖，全部已有实际发货路径。四个完整池194、275、415、472已加入默认物品券配置，1067个候选初始化通过；用户显式设置的池集合保持原样。

商品ID采用`2_000_100_000 + LoginBonusID`，SKU为`local_login_<ID>`。新名称、说明和确认文案追加到有效资源中，不覆盖官方文案；已启用的高级通行证文本也保留。所有商品保留完整PSC列和真实按钮模板4203149。

## 购买与期限

50只提交购买资格、固定PurchaseTime和限购次数，不发EBNS、不提前领第一天，也不改变钱包、名册或库存。46/47/50返回两类礼包合并后的完整PPF，避免客户端清表时丢失另一类购买记录。

按Type2原生显示公式计算：

1. `next_day = (购买时间转JST减4小时).date + 1天`。
2. 首领奖日为`max(源StartDate, next_day)`。
3. 截止日为`next_day + Expiration`，若源EndDate存在，再取较早者。

先加期限再裁剪起止，不因源开始日推迟而延长有效期。采用本地末日排他规则，`start_day <= 活动日 < end_day`。凌晨4点前购买可在当天4点开始领取，4点及之后购买从次日4点开始。若实际窗口为空，拒绝购买。

当前16组源EndDate均为空；ID41有效期60天，其余30天。PPF的两个日期D值为0，表示本地没有另设销售窗口。独立资格记录保存购买时间和领奖期限；EBNS只传LoginBonusID、LoginCount及PurchaseTime，客户端结合源配置计算显示期限，不把日奖期限误写成商品销售窗。

## 每日发放与重试

115和116共用同一资格账本，每活动每天最多投递一档。EBNS包含原LoginBonusID、当前序号和真实购买时间字符串；公共活动、回归及购买日奖合并成一个通知容器。购买接口不注册EBNS，不能靠50直接播放签到演出。

每档的全部奖励原子入箱。缺池、容量不足或暂不支持奖励时，记录一个pending；不把失败标成已领，也不补缺席日。已取得资格的pending过期后仍可重试，销售关闭不取消资格。Type22奖励物品名（含料理恢复物品）超过255字节原生单元时按501 `purchased_login_reward_unsupported`记pending，不让邮件写入方的503中止整次115或116。旧待发奖励未解决前不能通过提高购买上限再叠加同活动资格。

`purchased_login`版本1按连续purchase_id保存活动身份、购买请求、SKU、固定时间、计算窗口、逐档奖励指纹、已发邮件和pending。过期不删除记录，修改文案、窗口或上限不重置累计购买次数；源奖励变化时不偷偷替换冻结的未领奖励；定义变化的待发奖励用控制台的`purchased_login.resolve_changed`按购买ID处理（破坏性操作，确认短语`MIGRATE PURCHASED LOGIN <purchase_id> <ACTION>`，提交前自动备份），规则同回归签到：`redeliver`把该档及之后未领各档改用当前定义（当前目录缺的档保留旧定义）并补发，同活动当天已实发时按`purchased_login_daily_limit`继续待发，邮箱装不下或奖励暂不支持时同样继续待发；`void`把该档记为已用、不发邮件，之后各档保持原冻结定义；活动已不在出售目录或该档已无定义时只能`void`。

礼包回执保留原高级通行证结构，日奖购买使用带`kind=login`及purchase_id的独立身份字段。115使用投递标记版本4，116使用版本5，分开所有邮件来源。旧高级礼包回执保留原内容摘要及原PPF重建路径；新增日奖服务后，同一旧请求仍逐字节重放，随后新47请求返回合并目录。旧来源、状态、修订版或响应不再匹配时拒绝重放，不重新购买或发奖。所有发货和响应容量检查都在提交前完成。购买日奖分节的内容指纹由`content_version_for`按礼物箱配置求值，礼物箱的可选依赖或称号目录在115/116回执提交之后才接入时，旧回执照常逐字节重放；可重放的组合与409边界见`login-rewards.md`与`rank-rewards.md`。50号礼包回执的同类重放见`package-shop.md`。

## 后台验证

225项相关定向测试通过，汇总见`artifacts/purchased-login-validation.json`和`artifacts/purchased-login-verified-tests.xml`。覆盖16组168条奖励的实际发货参数、两类礼包先后购买、50仅取得资格、五天交替115/116领奖、跨日及过期待发、旧回执、重开与失败回滚。仅汇总各批已执行结果，没有运行全项目测试；最后的旧礼包兼容修复单独验证。

## 后续范围

本批未操作实际游戏或运行中的服务，未修改正式存档。后台流程通过不代表原生商店、签到动画和抽卡演出已实机验收。日奖商品来自完整本地活动表；官服其它组合礼包、推荐弹窗、实际平台支付与跨游戏资格不因此变成已实现。

控制台的`events.purchased_login`视图（实时）只读列出各次购买的活动、SKU、固定资格窗口与已发、作废计数和下一个购买ID，以及逐档的已发、作废、待发、未到（scheduled）与失效（lapsed：过了领奖期限）状态和冻结定义是否与当前出售目录一致；定义变化或活动已不在出售目录的待发档另附`repair`节，`command`为复用同一事务的`purchased_login.resolve_changed`，`targets`按purchase_id列出购买。出售开关、活动选择与购买上限经控制台配置切换修改`purchased-login-rules`，改变有效资源版本时属content档，需要关闭客户端并重新准备客户端资源。控制台没有删除购买记录或改写购买次数的命令，不能借此重新领取。
