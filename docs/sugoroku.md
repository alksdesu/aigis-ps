# 王国警备奖励棋盘

62读取本月已到达奖励，64标为已查看，63领取指定奖励。请求的REWARD.ID必须显式列出，不把空数组解释为领取全部。未达到的奖励不返回状态行；0为新到达，1为已查看，2为已领取。62返回完整快照，63/64只返回本次操作的行。

进度使用实际结晶消费账本的本月值，与115签到所用账本一致，不额外扣晶。周期按JST每月1日04:00切换。资源窗口开始包含、结束排除，排序为消费门槛及原资源顺序，保留同门槛多个奖励。

当前目录59条，现役56条。已支持其中54条：15条通用物品、27条单位、3条金币、9条下月最大魅力。单位通过现有标准初始模板入箱，这是明确的本地发货规则；表中并不包含官服附加成长值。三条金币各30000，类型由原生文本映射确认。GeneralItemID须在原生单元的255字节内，超长时整张目录拒绝加载，因为这些ID会写入新的PPT行；现有17条物品奖励最长21字节。

两条未支持项是RewardID1/10的十连物品券，分别引用pool33/32，现有候选概率表不完整。它们不能替换成pool350单抽券，也不把现有一名候选归一化为100%。原生`7DC400`有两种提交方式：全部领取时提交状态表里Status不为2的全部行，列表为空也照样发送；按门槛领取时整档提交同一ConsumeCrystal的全部RewardID，不看状态。客户端只在HTTP 200后继续，非200会弹出通信错误并按原包重发。因此63只领取请求里已到达、未领取且可投递的ID：不支持项跳过并保持已到达未领；已领ID照常回当前行；未知、过期或未到达的ID从回包中省略并记WARNING。一个也领不到时返回这些ID的当前行，不写回执，记WARNING（`Reward board 63 found nothing claimable ...`）。可领项全部不可投递时才回原501，单领1/10也回501。64遇到未知或未到达的ID仍回409并记WARNING；`7DA000`先发62再提交Status 0的行，正常不会触发。Type3当前无配置，免费/付费归属未确定；Type6属于已结束的旧体力设计，不开放。

## 下月容量的本地规则

Type5领奖直接在同一事务增加ExtendedMaxCharismaNextMonth，不生成虚构的扩容邮件。九条全部领取合计200。63没有PGP接收器，不能在其响应塞入容量字段；34完整GameParam回读会显示当前和下月值。

月初04:00先按旧上限结算此前的自然恢复，再以NextMonth替换当前扩容并清零NextMonth。第二个月到期。上限降低不扣除已经持有的体力，也不立即赠送新增上限对应的体力。跨多月最多处理两次有意义的容量边界，之后按零加成恢复。恢复药、结晶恢复和关卡结算共用此算法及配置的恢复间隔，默认180秒；关卡配置为600秒时不会被参数读取改回180秒。

33/34/35在回包前结算月份并预编码三个读取响应；62/63/64遇到尚未结算的月份明确要求先刷新。客户端停留页面跨月时是否自动执行上述刷新，仍属于原生待验项。PGP增量响应在存在容量账本时携带当前及下月扩容全名键，包含到期的0值。

## 持久化与重试

`sugoroku`保存按月份分组的状态、基线和发货邮件ID。来源明确的新建本地消费可以领奖；未知旧档已消费的门槛保留为已处理基线，不猜测历史领取并补发。后续新增消费及新月份正常累积；资源更新不清除已处理RewardID。历史上限1200个月、65535条，达到上限明确拒绝，不静默删除防重记录。

`monthly_capacity`独立保存当前月、当前及下月值与时钟。旧档没有该账本且扩容全为0时可初始化；非零旧扩容用控制台的`sugoroku.establish_capacity_baseline`建立基线（参数`period`为该扩容所属的业务月YYYY-MM，不晚于当前业务月；确认短语`MIGRATE CAPACITY <period>`，自动备份），不能把导入时刻猜成奖励来源。月度账本不保存体力扩容，建立基线时旧体力扩容随之清零，并在命令效果（`stamina`的前后值）与警告中列出；基线月早于当前业务月时，其后各月要到下一次33/34/35才翻转，期间棋盘操作等这次刷新。两类新增账本均保留其他存档字段。本轮没有迁移实际存档。

`sugoroku_history`保留16份精确请求回执与256个已处理请求摘要，客户端CT只作墙钟，不参与排序。已读（含空列表）和实际领奖写回执，一个也领不到的63不写。仅相同请求、相同月份、相同修订版及依赖指纹可重放；依赖指纹中的道具定义版本按其可达版本核对，称号目录在回执提交之后才接入时旧回执照常重放，伪造或不属于这些版本的摘要回409 `sugoroku_retry_stale`；发货邮件ID还必须与奖励账本逐项吻合。配置到期的旧包返回过期冲突，不误报历史损坏。回执记录回包显示的ID和本次实际领取的ID；旧水位格式的回执没有后者，读取时升级并按缺省值处理，重放时由同修订版下状态2的记录推出本次实际领取项。邮件、容量、状态与回执使用同一次CAS；容量不足、编码失败或并发冲突均不提交半笔奖励。

控制台`sugoroku.claim`（活动域）代玩家领取本月棋盘奖励，与63共用同一领取内核：先同步本月棋盘，只领请求中已到达、未领取且可投递的ID；下月容量直接记账，其余奖励入箱。参数须显式列出1–4096个互不重复的正ID。已领或不在本月棋盘上的ID跳过并给警告；投递不受支持的奖励保持已到达未领，同样给警告。一个也领不到时计划为空，连本月同步也不保存；可领项全部不可投递时与63一样回原501。月份未刷新（409 `sugoroku_refresh_required`/`capacity_refresh_required`，需客户端先完成33/34/35）、邮箱满、PresentID用尽、容量超出int32、棋盘或容量账本损坏时，返回与63相同的码和状态。控制台不写`sugoroku_history`：客户端已提交的63重发时，回执因修订号变化返回409 `sugoroku_retry_stale`；尚未到达服务器的63照常处理，被控制台领走的ID按已领回当前行，两种情况都不会重复发放。控制台领取不读回执，所以`sugoroku_history`损坏时63/64回503，控制台仍可领取。

后端目录、状态、事务、真实协议编码、邮件实领、容量跨月和关联恢复均有定向测试。原生游戏没有启动，界面与自动刷新行为仍待用户允许后验收。静态依据在`aigis_research/permanent-20261101/sugoroku-*-contract.md`及原始`sugoroku-contract.md`。
