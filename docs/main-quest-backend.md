# 普通主线后台初版

此模块在用户调整为“常驻功能、活动、战斗”的推进顺序前写入，完成必要后台检查后保留，后续战斗阶段再扩展和实机验收。未重启生产服务或操作游戏窗口。

## 范围与存档

QuestService处理77/78/81/82开战、80/83成功结算及ntwh57oy失败/撤退。Type0主线支持78/82的★4挑战，战术指南3001–3009同走此流程；模式注册、★奖励与其他模式见`docs/battle-modes.md`。独立76委任覆盖审定类型（当前Type0/2/8/16/18），接入1–3次批量扣费、掉落、任务及升阶奖励，见`docs/entrust.md`。复活与购买加成尚未实现；Boost.V只在大討伐按规则文件生效，其他模式接受并忽略。

开战核对关卡、前置通关、等级与候选掉落。候选来自固定主表快照和已校验地图Entry，按关卡记录的原始MaxRank选取，客户端不能直接指定奖励卡。体力扣除、抽选结果、规则和完整关卡定义存入同一SQLite修订版。服务构造时，启动表、角色与关卡使用同一公共主表快照；新导入表在重新构造服务后采用。

成功结算核对当前场次、协议编号、掉落位宽及已保存抽选结果。金币、经验、单位、物品、免费结晶、关卡状态和重试记录先组成候选存档，完整响应编码成功后才CAS提交。违反技术容量或任何发放失败均不提交半笔奖励；金币超过99,999,999的部分直接丢弃，不算失败。开战检查第一兵营有空位，正常结算允许奖励暂时超过玩法容量，不因此丢弃奖励。

quest_state使用独立版本字段，当前为schema 2，保存一个当前场次、最多8个关闭记录、最近256个已处理的开战与结算请求摘要（processed_keys）、礼物箱满时待补投的战斗礼物（原样奖励与份数），以及各模式的服务端私有进度`mode_progress`（如女神已发放的最高总星、大討伐的奖励水位）。键名`mode_progress`与“settle钩子只能改写自己策略名下的项”这条约定由`quest_modes.MODE_PROGRESS`统一定义，QuestService与各模式共用。内部场次号不伪装成原生BattleID。历史记录包含奖励汇总、响应和提交后的修订版，不保存请求正文或客户端队伍属性。普通日志仍只记录协议结构。

active中新增`unit_reservations`潜在角色奖励清单。开战预检并保存，其他发卡操作保留其行数、唯一编号和41响应空间；结算、退出或重开时释放。旧active缺少清单时可以直接结算、退出或重开，期间暂缓其他发卡。具体容量公式与兼容边界见`docs/unit-capacity.md`。

## 本地规则

以下是可配置本地规则，不冒充官方服务端算法。示例位于config/quest-rules.example.json，通过start-server.ps1的-QuestRulesFile或CLI的--quest-rules加载。

| 规则 | 默认值 |
|---|---|
| 有效候选抽选率 | 100%，实际取得仍以本次合法DP位为限 |
| 金币、经验 | 金币按公开资料口径（wikiwiki「各種ボーナス」：★2×1.2、★3×1.5；seesaawiki「金策」：報酬G増加能力与ゴールドゲットプラス（每次GG 130G）相乘、同类取最大）：单次金币=⌊(基础×gold_percent/100 + min(GoldGet, GG.I)次×每次金额)×星级×能力×MoneyUp⌋，每场GG最多1000次，不计GoldGet的模式为0；经验加成期内按原生1.2f、MoneyUp期内×1.5（作用于基础加GG）；入账以99,999,999封顶，超出部分丢弃，已高于上限的旧余额不变，REWARD.GOLD回实际入账额。详见`docs/battle-modes.md`结算一节 |
| 首次三星/★4 | QuestTable奖励Count≤0时1枚免费结晶（wikiwiki「ストーリーミッション」：「初★3クリア時｢神聖結晶｣1個獲得」，复刻继承通关信息、只发一次），返回完整PFC日期桶；免费桶加本次超过1000时整笔入礼物箱，礼物箱满时排队待下次结算补投；★4规则见公开资料（wikiwiki：★4「獲得EXP・獲得Gは通常通り」，难度结果4按★3、2按★2计金币） |
| 收集完成奖励卡等级 | 1级；普通掉落使用QuestTable.UnitLevel |
| 魅力恢复 | 每180秒1点；保留已有超上限余额 |
| 升阶 | 累计NextExp，魅力至少补至新上限；行动力不补、不自动恢复 |
| 扣费、重开、失败、撤退 | 官方口径（aigis1000.jp id 9370，2022-06-16维护后：全任务失败、ギブアップ不消耗魅力/体力/挑战权，リトライ不论次数只在通关时扣一次）：开战只预检并冻结成本，83成功结算时扣一次；失败/撤退无奖励、不扣费；旧规则下开战时已扣的场次结算不再扣、退出不退 |
| 无场次号的退出重试 | 5秒重复确认窗口 |

达到最高等级时经验停在最后一个合法阈值以内，REWARD显示实际增加值。通关位、三星位、★4位、掉落槽位与收集完成位分别更新，★4记MaxRank4。物品超Stack部分丢弃并回IOF。首次通关日期FirstDefeatDate为JST04业务日的原生日数（4点换日，与LastLoginDate同域），既有日期不覆盖；首次★结晶的取得日为JST民用日。剧情位0x40000000与MenuTutorialFlags保留，避免跳过首次剧情。GC.F7只保存设置，由36回读；PGC不识别F7，故不返回该键。

## 重试与未验边界

同一请求的重试不重复扣费或发奖。缓存同时核对主表/资源版本及提交后的完整存档修订版；后续修改发生后拒绝陈旧重放。108常开关窗同样改变有效资源版本：升级前开战、升级后才结算的场次，以及升级前已缓存的开战/结算回复的重发，都回409`quest_snapshot_changed`；升级前先结束战斗。客户端CT只作墙钟，不参与排序，时钟回拨或2038年后的负CT照常受理；场次记录仍保存开战与结算的CT，仅供查看。进行中场次的开战包重发回缓存回复；仍在8条历史中的开战包重发回409`quest_attempt_closed`，结算包按修订版重放或回409`quest_response_stale`；已被挤出历史但仍在已处理摘要中的开战或结算包回409`quest_request_stale`。结算没有场次标识，按当前场次的关卡、配对协议号与已保存抽选结果匹配，所以重开前生成、重开后才首次到达的旧结算包在三者都对得上时会结算新场次；原生客户端串行发包，实际难以出现。旧schema 1日志（CT水位）读取时升级，历史与进行中场次里的开战/结算摘要计入已处理，下次写入保存为schema 2；升级前已被挤出历史的旧请求不再算已处理。

原生PPU是追加操作。服务端存档幂等不等于客户端重复解析幂等；已消费后再次应用同一PPU可能造成客户端临时名单重复，仍需原生验证及必要的41权威重同步。修订版相同不能证明客户端尚未收到响应。

退出协议没有CT或场次号。同关前后两次相同退出无法无歧义区分：5秒内相同报文仅确认，保护刚重开的场次；极快的第二次合法退出也需窗口后重试。更晚到达的旧报文仍有歧义，不能宣称跨场次退出完全去重。

服务器没有模拟战斗过程，胜负与击杀数由客户端上报。队伍属性按原生结构解析；BL行与存档核对后只用于任务队伍条件，不写进存档。普通初始队员、完整新手剧情中断恢复和原生主页均未验收。

## 证据与验证

静态报告位于aigis_research/battle-results-20261101，包括battle-response-contract、treasure-list-contract、story-lifecycle-contract。奖励匹配采用原生范围归一化优先顺序。

控制器定向测试使用真实公共主表和资源，覆盖原生编码HTTP、保存后重开、重试、跨局完成奖励、配置保留、非法掉落拒绝、发奖失败回滚，以及时钟回拨后照常开战与结算、已处理请求拒绝、旧日志升级和缓存跨版本回归。经济辅助单独覆盖体力时间、浮点格式、等级阈值、超上限及溢出。未运行无关全量测试。
