# 觉醒后台流程

当前接入一觉7、技能觉醒8、二觉9，使用当前PC主表、职业表和原生收发契约。仍只做后台及原生编码HTTP验证，未启动游戏或重启正式服务。经典转职6在当前PC资格函数中恒不可用，没有擅自恢复旧功能。

## 资格与状态

| 操作 | 资格 | 成功变化 |
|---|---|---|
| 一觉7 | 原始阶段0、当前等级达到上限、好感至少100、存在合法觉醒路线 | 转阶段2，职业改为JobChange，显示形态重置0；按配置处理经验 |
| 二觉9 | 阶段2、好感至少100、选定分支实际开放 | TYPE1转阶段3，TYPE2转阶段4；保留累计经验，显示形态重置0 |
| 技能觉醒8 | 阶段至少2、当前技能满级、存在不同的觉醒技能、尚未执行技觉且未开启觉醒技能 | AD改为觉醒技能，AE仅开启bit2，B1改为1 |

三者保留角色UniqueID/GetIndex和未涉及的持久成长字段。技觉不清经验、技能等级或技能经验。目标可以锁定或编队，但王子和Card80不能作为目标：原生觉醒菜单按卡号排除它们，Card80的经典路线没有普通觉醒，即使资源为它们写入普通路线也照样拒绝。消耗材料不能是目标自身、王子、锁定或编队成员；普通实例同时核验CardID、GetIndex、UniqueID及实际所在兵营。

用户已选择一觉只带入溢出经验：`max(0, 原Exp - 原职业最高等级阈值)`。二觉保留全部当前经验。`--evolution-rules`或启动脚本`-EvolutionRulesFile`可加载`config/evolution-rules.example.json`；`first_awake_experience`支持`overflow`、`total`和`reset`，默认`overflow`。这些是明确的本地经验政策；原生一觉预览本来清零经验。

当前PC平台限制谓词虽保留字段访问，最终恒返回false；四个平台字段在当前主表也全为0。若后续更换客户端，仍需重新核实，不能从字段名称猜屏蔽规则。

## 素材与费用

一觉、二觉各四槽。前三槽由目标当前职业和同ConfigGroupID的所有稀有度配置生成替代条件；当前常见条件为对应职业类别的银卡至少30级，或金卡不限等级。第四槽匹配配置圣灵的初始职业与稀有度。技觉只有一个圣灵槽，同样按初始职业与稀有度匹配，不固定写死CardID。

服务器寻找四个不同材料位置的完整分配，每个普通实例只消耗一次；这是对未携带槽号的请求向量采用的本地兼容策略。仓库同卡可以重复引用，但按StorageType和CardID分别累计需求，不能混用两仓余额。

手动仓库素材的展示分支已穷尽：手动素材页只有当前兵营真实单位和已选仓库项的临时行，没有从仓库新增候选的入口，仓库卡只能先经自动选材进入选择集。所有可达分支上线形状相同，仓库行恒为`(1|2, 0, 0, 0, CardID, 0, 0)`，都对应自动选材的1级模板，所以银仓银卡不会凭空变成30级：金卡模板可以填普通槽，银卡模板不满足30级条件。客户端按本地圣灵仓名单决定类型，两仓卡号不相交，圣灵卡用Type1或银仓卡用Type2都整单拒绝。只能经脚本`DoBatchSelection`到达的批量重建在当前资源中不可达，它可能产生的异常形状继续由现有身份与兵营校验拒绝，不放宽。

7/8/9的普通素材均可来自已解锁额外兵营，七列中的StorageIndex必须等于实例AE的bits4..7，并通过原生兵营解锁范围检查。目标限定第一兵营，这与原生一致：觉醒目标菜单只取当前兵营表，离开兵舍移动菜单时表栈已清空，所以当前表恒为第一兵营；BASE序列化把StorageIndex固定为0，单表PPU接收器也无法应用额外兵营目标。额外兵营实例须先经118移回第一兵营；这类请求仍回501且不改错误码。位置、身份、保护和余额在同一CAS循环中核对；与合成共享素材解析器，聚合Type1/2不被当作普通实例。

金币及每种宝珠数量来自目标稀有度配置。7/9使用目标当前职业的两个宝珠字段，重复编码只扣一次。8按ClassData物理行序反查父职业：阶段2反查一次；阶段3/4先反查分支父级，再按阶段2反查，找不到时保留最近找到的职业。不能按CardID初始职业直接替代这种反查；当前资源存在重复父节点。

## 首次二觉奖励

只有原Rare5角色发放首次二觉同卡奖励，先进入礼物箱，不直接增加持有角色。用户选择每种原始CardID仅一次，旧二觉记录不追补。`evolution_rewards`独立台账在服务状态初始化时建立，基线包括原有阶段3/4实例及CardStatus.B3/B4二觉时间记录；不依赖完整养成模块可用，防止旧角色先被消耗而失去历史。已有台账只验证，不重算。

首奖使用资源中的初始状态PresentUnitData模板。模板技能等级0按原生初始化规范化为1，保留其余已核实的初始约束。原始CardID、显示替换CardID、资源模板PresentID、邮件唯一PresentID各自区分。复杂非初始模板保持未支持，不擅自降低其状态。

首奖回复新增PPT及保留全部旧字段的目标CardStatus行。A1列存在会触发提示，不把A1数值伪造为领奖标志；无首奖时发无列的空CardStatus组，清掉单例接收器上一次的临时A1，合并不改变全局角色历史。不能简单省略该组，也不能发带A1列的零行表。

原始资源缺少1605、1777、1785、2761四张卡的初始礼物模板，现已通过私服有效资源视图追加固定模板，服务器与客户端准备工具共用同一索引；二觉发奖和领取已验证，详见`docs/local-resources.md`。二觉奖励状态里的`known_template_gaps`也按同一索引（`LOCAL_TEMPLATE_CARDS`）列出主表中仍没有受支持初始模板的目标卡；有效资源视图下为空。显示别名513对应原卡498，原498已有模板453，不应误当成原卡缺失。

## 事务与回读

材料、金币、宝珠、角色更新、首奖及`evolution_history`回执同次CAS提交；完整41、受影响仓库读取、42及当前操作编码均在提交前预检。重试只在同一提交修订版和内容版本下回放；觉醒摘要里的可选来源（妖精乡、银之馆、二觉首奖、额外兵营容量）在回执提交时缺席、之后才接入时，回执摘要按提交时的来源子集计算仍算一致，旧回执原样回放。嵌套的可选输入同样按提交时核对：妖精乡与可写的银之馆也进入培养目录，觉醒目录的版本因此取其可达版本（培养目录缺这些仓库、或其中的妖精乡缺额外兵营容量时的版本）；妖精乡的版本含兵营容量，也取其缺兵营容量时的版本。所以妖精乡、银之馆与额外兵营容量不论先后接入，旧回执都照常回放。来源被移除、被替换或内容变化，以及摘要不属于任何可达组合时，按过期处理（409 `evolution_retry_stale`）；二觉首奖缺席时服务端不构建觉醒服务，实际不会后接入。回执有界，另记最近256个已处理请求摘要，已处理的请求再次发送返回409 `evolution_request_stale`。不按CT排序，时钟回拨或CT为负时照常受理，旧版水位历史读取时自动升级。被拒的7/8/9写WARNING日志：原生A7FDF0只在收到200后返回，任何HTTP错误都弹出通信错误并按原包重发，直到服务端受理，本地删除素材和觉醒演出只在成功后执行。仓库余量不足而拒绝时，另记一条诊断日志，写明StorageType、CardID、本次选择数和存档现有数，便于区分客户端本地余量过期与伪造请求；错误码与回执不变。按静态分析，这类确定性拒绝会让客户端一直停在通信错误与重发之间，每次重发各记一次日志。

7/9更新已有PPU的A7/A2/A3/A4/B0，8更新A7/AD/AE/B1，不复用新增角色接收器。三个觉醒注册都没有PFF/PSH接收器，响应不插入无效的仓库组。原生执行任务发送后不读结果，也不改本地仓库余量；本地余量要到下一次BaseSelect或素材页组装（先126再122）才整表刷新，静态可追的结果流程不读仓库余量，服务端无法也无需在7/8/9里刷新仓库。122/126始终返回事务后的权威快照；成功后的返回路径是否重新组装待实机确认。

7/8/9的事务内核为`EvolutionService.awaken(state, revision, request, now=, system=)`。选材与身份解析（`select`）、王子/锁定/编队保护（`protect`，只检查兵营素材）、报价、经`wallet_money.money_after_debit`扣费（余额不足回`evolution_money_insufficient`，恰好用尽且经验为0时回`evolution_native_balance`）、宝珠与仓库扣除、删除素材并保留UniqueID高水位、更新目标、9的首奖与任务计数，都在内核中完成。原生处理器只负责鉴权、回执、编码与CAS。控制台命令`units.evolve`用同一内核代玩家操作，按原生规则拒绝，不读也不写`evolution_history`；控制台没有会话，首奖邮件由预检的42回读核对。`tools.evolution`预览的`protection`段列出受保护的兵营素材及原因。
