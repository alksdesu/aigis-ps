# 活动通行证

158状态读取、159手动领奖和137重开读取已接入。当前主表有6组、264条奖励，包含48条免费结晶、134条单位模板、4条金币、78条物品奖励。原始六组Status均为2，原生可领取条件要求Status为1；可选本地复刻通过独立有效资源开放所选组，原始资源保持原样。

## 目录与资格

`EventPassConfig`中的非空NormalPassItemID开启一组；日期、Status和RequiredPoint沿零值/空值续行继承，PremiumPassItemID仅作用于本行。每行奖励必须保留所属积分档和轨道，同一积分档可以有多件奖励。ItemConfig、通行证与奖励物品名都按库存的256字节旧上限读取，超过256字节时整个目录拒绝加载；超过255字节原生单元的名称只供读取，新的通行证状态行、库存行和邮件仍由各自的写入方拒绝。

正常可领取窗口为`Status == 1`且StartDate、EndDate两端都含，按客户端整秒时钟判断（与皮肤商店同源：服务端时刻先落到客户端4 ms网格的整秒，再与客户端对StartDate/EndDate的读法比较；EndDate当秒内仍可领取，下一秒结束）。目录保存的StartDate/EndDate仍是资源里的整秒时刻，礼包的OpenDays/CloseDays与购买窗口照旧。内容版本的资格规则名为`status_1_and_inclusive_start_end_native_clock`。TimeLimit由原生用于替换界面的截止文案，没有在已核实的客户端领取判断中比较。服务不把这个展示字段自行当作另一个实际截止条件。

普通通行证物品的POSSESSION.Count就是累计EP，高级通行证物品Count大于0表示已取得高级资格。普通轨、高级轨分别比较`已领点位 < RequiredPoint <= EP`。领奖只读取这些数量，不扣积分、不消耗高级资格。后续取得高级资格，可以领取此前累计EP已满足的高级奖励。

原始382条普通任务的EventPassItemID/Point全部为空或0。帮助文本说明EP来自期间限定任务，但现有快照没有闭合其任务配置与结算时点。本地复刻另以明确配置为指定日常附加EP，不把这套本地安排冒充官服调度。

## 手动领取与邮件

158只接收公共请求头。159接收根EPI:S，当前原生菜单每次提交一个NormalPassItemID；本地也严格接受单组，不把空列表视为领取全部。服务验证窗口、已有水位、积分及高级资格后，将两个轨道所有新满足的完整积分档原子入箱。

料理转换为独立恢复邮件，随机券使用其真实池和抽数，单位使用现有初始模板，金币与结晶沿用共享邮件规则。任何奖励不支持、邮箱容量不足、编码或CAS失败都不部分推进水位。领取回SYSTEM、新PPT及受影响的EventPassStatus，不直接向角色或钱包发放奖励。奖励物品名超过255字节原生单元时，159回501 `event_pass_reward_unsupported`，不部分推进水位；116自动补领把该通行证保留为待处理。

奖励中的7个随机池443/448/451/452/454/470/471均完整，且全部候选初始化通过；它们和428一起列入物品券默认池（当前默认共44个池、83种券，见`item-summon-tickets.md`）。显式`--item-ticket-rules`仍完全采用指定集合，不会被默认值追加。

## 状态、重试与更新

原生三列为`ID:S`、`ReceivedNormalPoint:I`、`ReceivedPremiumPoint:I`。ID就是普通通行证物品ID，回包按ID合并。空组不会清除客户端旧记录；137返回全部已保存记录。

137在通行证目录或其邮件、物品券等依赖未就绪时仍返回全部已保存记录，并在启动诊断记为degraded；158、159和按ID选取的状态照常拒绝，存档损坏仍拒绝并记为refused。其他写入接口提交前回读137的预检同样按已保存记录处理，每次回读记一条WARNING（`Startup state was served outside a recorded load`），不再因此拒绝写入；159和116自动补领的预检也这样回读，但仍由通行证服务自身的就绪检查拒绝。

`event_pass_state`版本1保存原有水位基线、身份摘要以及每轨每档实际发放的RewardID、语义摘要和邮件ID。水位采用“实际完整投递的最高RequiredPoint”这一明确本地规则。现有合法三列可建立基线，未知历史通行证记录保持可读；不会把EP余额当作已领证明或自动改写历史水位。

相同RewardID或邮件ID不能用于第二次发奖；更新后把已发RewardID移到更高积分档也会拒绝重复发放。已领水位以下新增奖励默认不追补。普通/高级物品身份发生变化时用控制台的`event_pass.rebind_definition`把账本改绑到当前定义（确认短语`MIGRATE EVENT PASS`，自动备份），已投递记录保留；改绑之前，已有投递记录的通行证在159领取新到达的档位时回503 `event_pass_definition_changed`，服务端记一条WARNING，写明客户端会弹出通信错误、确认后原包重发，并点名该命令；控制台`event_pass.claim`同样以该码拒绝；116自动补领则把该通行证留在待处理（原因同为`event_pass_definition_changed`），不中止整次请求；改绑把旧身份移入该通行证的`archived`列表（按改绑先后排列，每项为definition、baseline_normal、baseline_premium与deliveries），新身份以当前原生水位为基线，水位及以下不补发，已发奖励不追回；每个身份的基线等于前一身份的水位，邮件ID在全部身份中唯一，奖励ID只在同一身份内唯一，全部通行证的归档合计不超过4096。等级奖励回执与159领取回执里的通行证邮件也在归档身份中查找。存档schema_version仍为1：旧档照常读取，但改绑过的存档不能再给旧版本服务读取。`events.event_pass`视图的`passes[].archived`按改绑先后列出归档旧身份的definition。身份核对为changed的通行证列在同一视图的`repair`节：`command`为`event_pass.rebind_definition`，`targets`按`pass_id`逐个列出，与其他账本的修复节同形；待处理原因仍为`event_pass_definition_changed`、但身份已与当前定义一致或已不在当前目录的通行证不列入，因为改绑会以409 `event_pass_rebind_unneeded`或501 `event_pass_unknown`拒绝。显示文字与尚未取得的新奖励不通过清空旧记录来处理。

`event_pass_history`保存16份回执及最近256个已处理请求摘要，不按CT排序，旧版水位历史读取时自动升级；`event_pass_delivery`独立记录最新实际投递清单。回执淘汰后重复的159按已处理拒绝（409 event_pass_request_stale，记WARNING）。已提交同包在修订版、状态、内容版本及清单均一致时可直接重放，不再次读取时钟或发奖；新的请求才核对当前领取窗口。内容版本按`replayable_content_versions()`核对，集合是道具定义各可达版本与通行证目录两种窗口规则版本的全部组合。称号目录在回执提交之后才接入时，或回执提交时通行证窗口仍按JST时刻比较时（目录版本的资格规则名为`status_1_and_inclusive_start_end_jst`），旧159回执都照常逐字节重放；伪造或不属于这些组合的摘要回409 `event_pass_retry_stale`。
