# 官服召唤调度采集

用户选择先补采官服调度，再实现召唤，不使用本地生成的替代开放列表。

当前用户要求先继续无需进游戏的功能。采集等待进程已停止，本轮没有生成官服调度样本；恢复采集后才继续实现依赖CSS/CSP的召唤交易。

下一次从 DMM 启动原版时，可先用 `client/capture-all.ps1 -Mode Check` 检查，再运行 `client/capture-all.ps1 -Mode Wait -Timeout 7200` 等待。这个 [一键入口](capture-all.md) 同时采主表、资源版本与全部允许的业务响应，并导出首份完整的 70/71 配对到本页所述调度目录。只打开召唤菜单即可等待调度自然返回，不需要抽卡或购买。该编排尚未实机验证，以下独立采集入口继续保留。

私服对70/71回显式空调度（`summon_schedule.SummonScheduleService`）：70回SYSTEM与无子节点的CSS、FPR、SH、GacyaStatus、LCC、PLC，71回SYSTEM与无子节点的CSP，组名取自`schedule_capture.SCHEDULE_GROUPS`，编码为`<CSS></CSS>`这类空元素，不列列定义；鉴权之外不读写存档，也不取时钟。原生A7EE90把无子节点的组当作零行并以空表替换旧内容，FPR、SH的入口先把计数清零，所以客户端不列出任何阵容、召唤活动与召唤包，主页横幅与菜单入口不再停在70/71的501弹窗。这不是官服调度：采集仍只附加原版客户端、观察官服70/71的自然返回，召唤11/12/13仍未实现，补采官服调度的需求不变。将来实现召唤时70必须回完整的当前状态，因为召唤成功后客户端会重读70，继续回空组会清掉刚写入的计数。以上未经实机核对。

`client/capture-schedule.ps1 -Mode Wait` 等待原版Aigis_r.exe，或附加到已运行且路径、SHA256完全匹配的原版。进入召喚页面时观察70/71自然返回，不主动发请求，不执行抽卡或购买。`-Mode Check`只检查本地文件与挂点；`-Mode Pid -ProcessId <PID>`用于明确指定已有原版进程。

采集在A801D0解码后入口读取响应，先核对原版路径、x86、代码指纹，再用返回地址、注册号和vtable限定70/71。游戏进程内先筛选业务组、删除凭证和身份列，然后才发送给宿主；Python再次解析并检查过滤前后结构一致，写盘只接受已经过滤的内容。

- 70：CSS、FPR、SH、GacyaStatus、LCC、PLC；至少必须有CSS。
- 71：CSP；至少必须有CSP。
- SYSTEM、未知顶层组、认证信息及请求正文不保存。
- 合法空组保留；没有收到的组记为缺失，不合成空表。

结果位于`runtime/schedule-captures/schedule-时间-PID-随机值/`。`state.json`显示进度，`manifest.json`记录最终完整性，编号XML文件保存业务数据。只有同一附加进程内最新70之后的71构成完整配对；新70被拒绝时也清除旧配对，避免混用旧数据。

默认总等待时间900秒，完整配对后自动脱离进程。900秒包含等待原版启动的时间，附加进程和加载代理的时间不计入；到期时已送达的响应仍会处理，到期后才到达的不再延长采集。代理消息超出本地队列容量时以`schedule_queue_overflow`结束。超时、队列溢出、进程退出或异常时保留已验证的部分数据，并列出缺失项；不能将部分文件当作完整调度导入私服。所有输出都留在111项目内。

70/71以外的官服响应（如12/13抽卡、108购买）用通用响应采集器`client/capture-responses.ps1`，见`response-capture.md`；它单独运行时也能记下70/71，但不做同一轮配对。一键入口会额外检查配对并导出本采集器的常规格式，配对完成前遇到拒收的70会清除旧候选。`run.json`的调度分项与调度`manifest.json`都需核对，通用响应正常停止不能代表调度完整。

挂点依据见`aigis_research/permanent-20261101/capture-schedule-contract.md`。纯提取70项、宿主流程及JavaScript联合91项分别通过定向测试；JavaScript测试在隔离VM中验证，不代替真实采集验收。
