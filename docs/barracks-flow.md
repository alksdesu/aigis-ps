# 额外兵营

注册17购买下一座额外兵营，请求只有公共头。当前已核对版本每座消耗30结晶，第一座需要Rank25，最多两座；按已确认本地钱包规则先免费、后付费，同类先旧日期。增加HaveUnitMaxSizeBuy高16位，低16位保留，并同事务累计30结晶月消费；回应PPC/PFC完整类别余额、PGC.A5及PGP2.C1键值，不额外发奖。

注册118接收根DEST和BASE.A7/AB，最多10个同源实例。支持第一兵营与第二/第三兵营之间四个方向，未实现额外兵营之间直达。服务器校验准确身份、源/目标已解锁及目标容量；向外转移排除王子和已编队角色，允许锁定角色。回到第一兵营可恢复历史异常编队引用。只改AE的bits4..7，保留有符号高位、锁、技觉、成长和所有身份。

客户端发送前已在本地搬行并改AE，算式与服务器相同。PPU接收器CUpdateUnitList（`A67C00`）只在第一兵营按GetIndex定位，找不到时改写其最后一个单位，所以迁往第二/第三兵营时回零行PPU（原生只刷新、不写数据）；迁回第一兵营照旧回完整21字段。同一规则用于10与119：第二/第三兵营单位的行不回，没有剩余行时回零行PPU。内容策略为2，修复前的搬移回执及由其派生的购买回执重试按过期处理。

完整41、36、本次响应以及当前已冻结战斗奖励的技术空间均在提交前预检。转移不发新单位、不占新身份，业务满额与全局技术上限分别处理。旧活动战斗缺少奖励预留信息时需先结束该战斗，再进行会改变位置的转移。此处不扩展战斗玩法。

购买和转移共用`barracks_history`（schema2，共享RequestLedger），最多16条完整回执及最近256个已处理请求摘要；CT只是客户端墙钟，不作排序，时钟回拨的新请求照常处理；旧schema1历史读取时自动升级并可精确重放。17与118被拒时都以WARNING记录：原生客户端弹出通信错误并按原包重发，直到服务端接受；118的897630在发送前已在本地搬行。回执绑定内容版本和提交修订版；旧请求不能重复买下一座或在之后重新搬动角色。完全已经处于目标兵营的首次请求只记录回执，单位值保持不变；再次相同请求不再提交。

购买使用新增purchase_content_version并校验当前钱包/C1的完整回包，预检35和43/44；原content_version继续用于118搬移，搬移不更新月消费账本。购买新动作只捕获一次服务器时间，缓存重放不取时钟或重复计费，见login-rewards.md。

控制台（存储域）的`barracks.grant_slot`只把HaveUnitMaxSizeBuy的高16位加一，低16位旧购买计数不动；不扣水晶、不计月消费、不检查25级，最多两座额外兵营，买满返回409 barracks_purchase_limit。`barracks.transfer`与118规则相同；拒绝顺序也与118相同，先校验目标兵营与单位选择，再查兵营容量服务是否在启动后变化（503 `barracks_catalog_changed`）、存档、GameParam（不可加载时如金币为负，503 `invalid_player_state`）与兵营用量；目标就是当前兵营时不改状态，给出警告，战斗预留试算由控制台units域的预检完成。两条命令都不写barracks_history回执；字段归属表中Config.HaveUnitMaxSizeBuy只归`barracks.grant_slot`。单位锁定的控制台命令见`implementation.md`。
