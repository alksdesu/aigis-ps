# 普通活动签到

115与116共用`EventLoginService`和独立活动账本。普通印章、新手七日、料理、等级奖励和通行证到期奖励保留各自来源；同一活动当天先从任意一条路径成功领取，另一条路径不会再发相同档位。

## 默认范围与配置

当前EventStamp有136组、1236条奖励：119组普通Type0、1组回归Type1、16组购买绑定Type2。默认按原始有限窗口选择普通活动，不根据奖励表存在就开放回归或购买资格。普通活动4、90、91缺结束日期，且包含新号限定说明，默认不自动发放。

日期规则：活动日为日本时间减4小时后的日期，`start_date <= day < end_date`。原生能证明04:00日切及两接口共用展示；末日排除已由官方期间证实，与官方公告一致（官方结束时刻全部写「EndDate当天3:59」，资源EndDate与官方结束日同日，最后一个有效JST04日即EndDate前一天；逐活动核对见`aigis_research/events-20261101/login-window-boundaries.md`），代码不变。首日按StartDate整个JST04日开放；官方从StartDate当天维护结束（多为15:00–19:00）或4:00开始，本地没有维护窗口，首日最多早开十几个小时，仍只发第1天，这是本地简化（`aigis_research/events-20261101/login-window-boundaries.md`第3节）。

在2026-11-01活动日，默认可发的是135组，窗口为2026-10-22至2026-11-06。首次观察从第1档开始，实际登录每一天递增一档，最多十档；不补此前缺席日期。其十个单位模板全部已有发货支持。

`config/event-login-rules.example.json`保留默认策略。可通过`--event-login-rules`或PowerShell的`-EventLoginRulesFile`加载：

- `enabled`：是否发放；关闭时不清历史或待发记录。
- `campaign_ids`：明确选择的普通活动ID；`null`选择全部符合条件的公共窗口。
- `revivals`：按活动ID指定固定的`start_date`和`end_date`，格式为YYYY-MM-DD。示例`event-login-revival.example.json`开放55组，包含现有148目录的自选券。

复刻仅修改所选普通活动的资源日期，奖励、资格类型和剧情展示资料保持原值。它为缺少原资格的历史活动提供明确的本地资格政策，不还原官服历史资格。重复移动窗口不会重置已领取档位。Type1、Type2、相对期限和暂停规则不能通过该配置改成普通签到。

## 发奖与待处理

同一日档可能有多件奖励，必须整体入箱后才递增次数。单位按模板入箱，金币和免费结晶不直接入余额；自选券、随机券和料理分别复用已有专用领取流程。普通活动130使用的完整463池已纳入默认物品券范围，活动签到131第7日十连券所用的完整464池同样默认开放，用户显式指定的池集合保持原样。购买型136使用的472池随购买后每日领奖另行加入默认，见`purchased-login-rewards.md`。默认池下复刻活动75/90/92/104后，19104（池325）、19122（池375，规则9）、19123（池376，规则6）、19125（池386，规则6）与item_smn_ticket_blacknohave_10029（池423，未所持）都可入箱和领取；此前因item_summon_unsupported或summon_ticket_pool_disabled留下的pending，在新版本下可以重试。

每活动最多保留一个已经在有效窗口取得资格的待发档位。遇到缺池、未支持奖励或容量不足时，记录原因并保留资格，不吞奖励，也不阻塞能正常投递的其它活动和普通签到。之后的新请求可在同日或活动结束后重试这一档；缺席日不累计欠账。成功补领当天不再发该活动下一档。Type22奖励物品名超过255字节原生单元时按501 `event_login_reward_unsupported`记为pending，不让邮件写入方的503中止整次115或116。

资源更新改变待发奖励定义时保留待处理记录，不把已取得的奖励悄悄换成新物品；用控制台的`event_login.resolve_changed`按活动处理（破坏性操作，确认短语`MIGRATE EVENT LOGIN <campaign_id> <ACTION>`，提交前自动备份）：`redeliver`按当前定义补发，邮箱装不下或奖励暂不支持时按新定义继续待发，由115/116重试；`void`把该档记为已用而不发邮件（`deliveries`里该档`mail_ids`为空、投递日取资格日，控制台视图记为voided），下一个签到日照常领下一档；活动已退休或该档已无定义时只能`void`。已退休或暂不支持的活动记录也保留，避免阻塞其它活动。未知存档结构、非法邮件来源等数据问题仍使整个事务失败，不当作普通缺货吞掉。

115先处理普通签到，再尝试活动；116依次处理等级、通行证到期、活动。每接口的所有成功结果在同一次CAS中提交，编码失败或并发冲突不会留下半笔发奖。各活动的组合响应也在投递前检查容量。

## 协议与存档

只在本次实际发出活动奖励时返回EBNS，三列为`LoginBonusID:I`、`LoginCount:I`、`PurchaseTime:S`，普通活动的PurchaseTime为空字符串。PPT包含真实新邮件。PLC是召唤活动计数，与签到无关，不因此清空或伪造。

`event_login`版本1按活动保存连续已发档位、奖励指纹、取得资格日、实际投递日、邮件ID及最多一个pending。没有实际活动或既有记录时不新增空账本。每个实际投递日最多一个档位；时间倒退不能重置计数。

115保留旧内容指纹，新的领取指纹包含活动依赖，投递标记版本2分别保存普通邮件和活动结果。116保留旧版本1/2回执，新标记版本3分别记录等级、通行证和活动邮件。旧回执重放不会读取新时间或补活动奖励，新回执还会核对来源、永久记录、奖励内容及完整响应。公共活动分节的内容指纹由`content_version_for`按礼物箱配置求值，礼物箱的可选依赖或称号目录在115/116回执提交之后才接入时，旧回执照常逐字节重放；可重放的组合与409边界见`login-rewards.md`与`rank-rewards.md`。

初始化允许保留已经领取掉的邮件历史和旧奖励定义；精确重放则要求当前修订版、内容与回执一致。不能清账本实现重复领取。

## 客户端与后续管理

默认源窗口不改变有效资源版本；显式复刻的日期覆盖与其它资源覆盖一起生成新版本。独立客户端准备程序支持同名参数，并在计划、复制和结束检查中固定同一规则。实际客户端必须使用与服务端相同的复刻配置。

控制台复用同一目录、规则、待发原因和共享发奖事务。调整活动窗口不等于重置进度，手工解决缺池或错误定义也不能删除已发记录。控制台的`events.event_login`视图只读列出已发、作废与待发档位，待发档的原因与资格日，以及各档冻结定义是否与当前目录一致；定义变化或当前目录已无定义的待发档另附`repair`节（`command`为`event_login.resolve_changed`，`targets`按campaign_id列出对应活动）；`event-login-rules`可经配置切换修改，复刻窗口改变有效资源版本时属content档，需要关闭客户端并重新准备客户端资源。

本批没有运行游戏、启动或重启实际服务，也没有改原客户端或正式存档。后台验证不证明原生签到动画和主页流程已验收。回归、购买绑定、旧DailyGift、投票和依赖战斗的活动继续保留在计划内。

回归Type1随后已由独立轮次服务接入，见`comeback-login-rewards.md`；不改变本文公共活动账本或将回归奖励并入其永久序号。购买绑定Type2随后由购买后每日领奖礼包接入，见`purchased-login-rewards.md`；旧DailyGift与投票也已分别接入，见`daily-gifts.md`与`vote-events.md`；其余剩余范围仍保留。
