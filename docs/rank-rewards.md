# 等级奖励

等级奖励已接入战斗结算和主页116领取。当前本地发放目录取`cfgRnkbns`与`RewardConfig`中等级条件的交集，共118项；114项可按现有邮件能力发放，另外4项保留待发。这个交集是明确的本地开放规则，客户端目录本身不能证明官服的完整调度。

## 触发与发放

原生等级条件为`旧等级 < 奖励等级 <= 新等级`。普通结算80/83使用同一次存档事务保存经验、等级、关卡结果、奖励资格和新增邮件；返回新增PPT。角色合成的经验属于角色实例，不触发玩家等级奖励。

主页116只接收公共头及根字段`SHOP:I=0`、`NUM:I=0`、`DmmPremiumReceiverId:I=0`。原生填充A56F90会在公共头之后再追加一个相同的PlatformCode（137的A62B70同样如此），解析器对116/137接受一或两个相同值。它核对已保存等级并尝试投递待发项，响应SYSTEM和本次新增PPT；只接入等级奖励时，无新增只回SYSTEM，其他已接入来源按下文各自追加子项。启用通行证自动结算后，同次116还可返回自动邮件和对应EventPassStatus，见`event-pass-auto.md`；某个通行证因邮箱容量、暂不支持的奖励、回复容量不足、ID超出原生单元或物品身份变化待改绑而不能补领时，只把它记为待处理，等级奖励和其他通行证照常投递。非零DMM会员领取分支明确未实现。该接口不接收客户端指定的等级或奖励ID。

116不返回RANKUP。原生该字段会用旧等级0重建奖励提示，单次补发可能重复显示历史奖励；战斗结果已有正常的旧、新等级提示。`cfgRnkbns._FlagID`是教程提示位，不能用于判断奖励是否发过，也不修改`MenuTutorialFlags`或`MissionRewardFlags2`。

等级10的Reward78发配置1自选券，等级25的Reward107发配置2自选券。它们进入普通邮箱后，由已有Type20单券流程选卡、生成新实例；其他单位模板、结晶和物品继续使用共享邮件服务。

## 存档与待发

`rank_rewards`版本1保存基线等级、已观察等级，以及按RewardID记录的奖励等级、语义摘要、pending/delivered状态、实际邮件ID和待发原因。奖励一旦投递，即使邮件已经领取或删除，也不会再次生成。

新建存档的基线为0，仍使用已确认的初始角色和等级；当前目录没有等级1的普通队员发放。既有无账本存档以接入时的实际等级建立基线，保留现有进度，不猜测过去是否领取过。此迁移策略不会追补旧等级奖励。

邮箱容量不足、邮件身份耗尽或奖励尚未支持时，该项继续pending，其他可投递项继续处理。非法数据或依赖版本不一致会中止整个事务。当前待发项为Reward143/144/145（`item_smn_ticket_10001`、pool8）和Reward180（`item_smn_ticket_15001`、pool16）；虽然数量已确认为1，其卡池仍不完整，不替换卡池或归一化残缺概率。

奖励资格记录冻结语义摘要。资源更新如果改变同一RewardID的实际奖励，旧pending保留原摘要和明确原因，用控制台的`rank_rewards.resolve_changed`按等级处理（确认短语`MIGRATE RANK <rank> REWARDS <ACTION>`，自动备份）：`redeliver`按当前定义改写摘要并立即补发成邮件，邮箱装不下时按新定义继续pending，当前目录已没有该奖励时回409要求改用void；`void`删除该pending条目，已观察等级不变，之后不再发放，审计记录保留前后值；显示文字或资源行号变化不改变语义。已投递记录保留，不因更新重新发放。新进程需加载完整且通过校验的资源及规则后，116才能重试待发项。

`rank_reward_history`保存最多16份回执，另保留最近256个已处理请求摘要（CT不作排序，旧版水位历史读取时自动升级，回执淘汰后的已处理同包返回409 `rank_reward_request_stale`并记WARNING），`rank_reward_delivery`独立记录最新请求实际投递的邮件ID。版本1继续支持纯等级回执；版本2将等级和自动通行证邮件分组记录，使用独立的116派发指纹。重试核对身份、当前修订版、完整状态、依赖版本和发件清单；其他操作改变存档后，旧回包不再重放。并发冲突重新读取当前存档后处理。

普通活动签到随后接入同一116事务，版本3分别记录等级、通行证与活动邮件。115/116共用活动进度，旧版本1/2回执不补发新活动奖励。活动来源校验、待发补领和22项116专项见`event-login-rewards.md`；等级增长的`apply`本身不触发活动签到。

回归签到进一步采用版本4标记，将回归轮次结果作为第四类来源。新116先记录登录观察，再结算各来源；旧版本1/2/3回执不观察新登录或补发回归奖励。D0/D1按完整字段名返回，公共与回归结果合并为单个EBNS，见`comeback-login-rewards.md`。

购买日奖使用版本5标记，增加固定purchase_id及PurchaseTime的第五类来源。115/116共用资格和日序号，公共、回归、购买日奖合并为一个EBNS；旧版本1–4回执不补发新购买奖励。新116使用同一时间和事务处理全部来源，见`purchased-login-rewards.md`。

DailyGift使用版本6标记，作为第六类邮件来源同事务保存。它只追加实际PPT，不增加EBNS；所有旧版本1–5仍按原摘要和响应重放。独立资格日允许在一个请求中补投多个实际登录日取得的pending，不能从日历缺口补发未登录的奖励，见`daily-gifts.md`。

投票日票与料理通知使用版本7；LetsTD使用列表式版本8，在任一固定版本的section之后列出扩展。投票普通票到期折金提示使用版本9，在固定section与可选LetsTD之后追加`vote_expiry_notifications`，保存本次`ItemExchange.Gold`提示和累计提示数量；它不产生新邮件。新摘要接在LetsTD之后，接入提示服务不改变版本1–8的摘要和旧回执字节。规则见`vote-login-refresh.md`。强袭挑战权折金提示使用版本10，在固定section与可选的LetsTD、`vote_expiry_notifications`之后追加`vote_assault_notifications`，保存本次`RET.msid`提示和累计提示数量；它不产生新邮件。新摘要接在普通票折金提示之后，接入提示服务不改变版本1–9的摘要和旧回执字节；一旦写入版本10回执，之后的构建必须继续提供该提示服务。cli在投票交易就绪时总是装配两种提示服务，所以默认新写版本10；标记带提示section而服务缺失时initialize回503 `rank_vote_expiry_unavailable`或`rank_vote_assault_unavailable`，存档已有提示账本而服务缺失时启动回503 `vote_expiry_notifications_unavailable`或`vote_assault_notifications_unavailable`，版本8/9的旧回执照常重放。

可选服务在回执提交之后才接入时，旧回执按提交时的服务配置精确重放。回执没有记录的section视为当时没有服务，包括固定版本中高于其等级的section和全部扩展，以及列表式版本8–10中`sections`未列出的LetsTD、到期提示和RET。已记录的固定section对缺席服务只写空占位，所以重放接受当前已接入服务的各种子集，但最后一个固定section至少要有一个自身服务。命中后按那份配置重建回包，后接入服务的回归参数、日票库存、料理通知和LetsTD提示都不会混入旧回包，也不读新时钟。礼物箱配置也计入枚举：116的基础摘要必需道具定义、召唤券、道具券与自选券，缺任一项的配置当时不会有116服务；回复道具目录在回执提交时缺席、之后接入，或称号目录后接入改变道具定义的版本时，基础摘要与通行证、强袭挑战权提示及公共活动、回归、购买日奖、DailyGift、LetsTD各分节摘要都按提交时的礼物箱配置求值，旧回执照常精确重放。`replayable_content_versions()`给出基础摘要在这些配置下的版本，供委任76核对。接入自动领取通行证时，每个礼物箱配置另有一份旧窗口变体：通行证分节及其后各分节摘要按旧规则名`status_1_and_inclusive_start_end_jst`的通行证目录版本求值，按JST时刻比较窗口时提交的116回执照常精确重放。基础摘要不含通行证目录，`replayable_content_versions()`不因此变化。不属于任何已提交配置的摘要仍回409 `rank_reward_retry_stale`；回执提交时已接入的服务被移除后同样回409。

## 后续管理与边界

控制台的`wallet.experience.add`在同一次提交中经同一等级奖励服务发放升级奖励，`rank_rewards.retry_pending`重试pending项，定义变化的pending由`rank_rewards.resolve_changed`按redeliver/void显式处理（见上文），`progress.rank_rewards`视图分别展示基线、观察等级、待发原因和已投递记录。回退等级、改写历史奖励或重新授予没有别的入口，不能通过删账本、改教程位或清回执重发。

其他RewardConfig条件、DMM会员奖励、活动与礼包来源不属于本模块。普通召唤仍待CSS/CSP采集；四项缺池券仍有未完成依赖。此次只有后台和定向验证，原生等级动画、主页领取及自选券界面尚未实机验收。

静态依据：`aigis_research/permanent-20261101/reward-config-contract.md`、`reward-config-readiness.md`、`reward-config-impact.md`及`reward-config-evidence`。
