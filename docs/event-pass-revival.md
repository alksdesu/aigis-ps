# 本地通行证复刻与任务积分

复刻通过显式配置启用。服务端资源、下载索引和独立客户端准备过程使用同一份配置；未配置时继续使用原有资源版本。原始客户端、缓存资源与公共主表不被覆盖。

## 复刻配置

`config/event-pass-revival.example.json` 选择 `event_pass_20261015`，把以下积分附加到现有日常奖励。它是本地规则，不代表官服的期间限定任务安排。

| 日常条件 | ConditionID | EP |
| --- | --- | --- |
| 登录 | 1611 | 2 |
| 通关三次 | 1607 | 4 |
| 送礼实际增加好感度 | 1608 | 4 |
| 合成 | 1609 | 4 |
| 完成全部日常 | 1610 | 6 |

每天全部完成并领奖共20 EP，五天可到该通行证的100 EP最终档。高级轨道仍要求对应高级通行证物品，启用复刻不会赠送高级资格。

`pass_id` 必须是当前资源已有的普通通行证ID。`mission_points` 只允许现有普通日常，不改变完成条件、基础奖励、排序或日切规则。遇到未知任务、已有不同EP绑定或其他已开放通行证时间重叠时拒绝生成覆盖。复刻会新开通行证状态行，`pass_id`仍须在255字节原生单元内；资源中的通行证与奖励物品名按通行证目录的256字节旧上限校验，覆盖层与目录接受同一张表。

可选 `start_at`、`end_at` 使用日本时间原生格式或带时区ISO时间；省略时继承固定的资源时间，不按启动时间自动移动。`display_text` 默认为「ローカル復刻」。重启同一配置生成同一资源版本，不能用移动截止时间反复领取旧奖励。

服务端Python参数为 `--event-pass-revival`，PowerShell参数为 `-EventPassRevivalFile`。独立客户端的 `prepare_client.py` 和 `prepare-client.ps1` 使用同名参数；两端必须选择同一配置。已有客户端副本需要重新准备以取得匹配的有效资源，启动器继续校验服务端版本。本批后台开发不自动准备或启动实际客户端。

## 任务领奖

原生58/59响应支持 `POSSESSION`，EP通过普通通行证物品的绝对持有量更新。54读取、60标记已读和任务刚达成时均不加分；成功领取基础奖励时才一起入账，这是本地明确采用的发放时点。

基础奖励继续入礼物箱，任务状态、邮件、EP和回执在同一个存档事务中提交。任何奖励、容量或响应编码检查失败都不提交。已达到EP物品上限时只加剩余容量，原有超上限数量保留；活动窗口外不加EP。未能计入的积分不欠账，也不阻塞基础任务领奖。

任务响应只回本次实际增加的EP物品，不把积分伪装成邮件，也不提前提升通行证领取水位。158/159及116自动补领沿用独立的通行证奖励流程。保存前同时检查129与137的完整库存回读一致性。

## 旧档与防重复

`mission_ep_bindings` 记录原始任务定义与前次EP绑定。只有能够从原始定义证明“仅EP绑定改变”的未领取记录才更新定义指纹；进度、已读、实例集合和周期保持。已经领取的记录不重开、不补EP，未知定义差异仍由原有任务校验拒绝。

更换积分值、切换已有通行证或停用复刻使用同一迁移规则。普通任务没有EP改动且存档没有绑定记录时不新增该结构。旧通行证积分、两轨领取记录和其他奖励历史保留，复刻同一个ID不会自动重置已经领取的档位。

`mission_history` 的EP领奖回执增加 `event_pass_points`，记录每种普通通行证请求积分、实际入账、前后库存、溢出和窗口外未发数量。`mission_pass_delivery` 独立保存最近一次EP领奖来源。重放核对来源、状态摘要、实际库存和响应，不再加分；旧的纯邮件回执结构继续兼容。

## 边界

本地日常积分替代方案不等于已采齐官服PT3期间限定任务。高级资格已通过独立免费礼包接入，见`package-shop.md`；活动战斗依赖和原生客户端界面仍分别待接通或实机验收。当前只进行资源、协议、事务与旧档兼容的定向测试。
