# 邮件奖励与库存领取

已接通单位、免费结晶、金币、11种固定物品邮件，以及479项库存物品的入箱、42读取和领取。其中116项普通物品支持117批领，242项战神加护、38项服装及83项称号通过1/2单领，117批领会跳过它们并保留邮件。称号有独立目录和资格规则，见emblems.md。后台按真实主表与原生编码测试；原生界面验收仍待用户恢复实机。

固定类型映射来自原生持有量getter，不能用商店InventoryConfig重映射。类型22的普通范围为EffectType 4/5/6/7/9、正Stack、ReceiveAction和ReceiveConfirmation为0、空EventID，计116项。新增加护12及服装13另外验证类别、唯一库存和逐封领取标记，计280项，详见owned-item-rewards.md。CanPresent不是这条领取路径的资格判断，不据此排除已有原生领取证据的物品。

恢复药和172种料理现已按独立恢复流程接入，见`present-recovery.md`；它们不增加库存。服装领取现已联动解锁资格及取得任务；加护持有和独立开关均已接入，战斗效果仍待验收。随机券、自选券及称号各有独立流程，范围见`item-summon-tickets.md`、`select-tickets.md`和`emblems.md`。

## 共享接口与存档

`PresentItemCatalog`冻结有关物品字段、固定类型绑定和规则指纹，并校验与`PossessionService`的定义一致。称号目录接入后内容版本改为含称号的版本，`replayable_content_versions()`另给出不含称号时的版本；把道具定义版本写进回执摘要的服务（序列码、任务、57投票奖励、活动通行证、双六、115/116及其子服务、LetsTD，经任务的名声149–151与皮肤商店156，以及经任务与116的委任76）据此在称号目录后接入时照常重放旧回执，不属于这些版本的摘要仍按各自规则处理。`PresentService`通过可选的`possessions`依赖启用物品邮件；旧调用方不提供该依赖时，仍可处理原有单位、免费结晶和金币。

`PresentService.templates`以只读映射公开已核实的模板ID到CardID，`PresentItemCatalog.rows`以只读映射公开已验证的ItemConfigTable行，控制台视图和其他服务不必读取私有字段。`PresentService.history(state, revision)`公开校验后的领取回执列表，供控制台presents.receipts视图读取。结晶领取容量由`crystal_wallet.claim_crystals_fit`判断（原生65EDE0：付费不超过1000、免费加本次不超过1000、合计加本次不超过2000），117逐封累计时用`claim_crystal_space`，控制台`wallet.crystals.credit_free`按同一规则判断，超出部分提示改发free_crystal邮件；它与战斗结算的`free_crystals_fit`不同，后者只按免费桶决定直接入账还是改发邮件。金币经`wallet_money`按`GOLD_LIMIT`判断，多封金币合计超过int32同样按`present_gold_capacity`拒绝。

`enqueue`新增三种奖励输入：

```python
{"kind": "gold", "amount": 1000, "description": "reward"}
{"kind": "legacy_item", "present_type": 3, "amount": 2, "description": "reward"}
{"kind": "item", "item_id": "gift_0000_bouquet", "amount": 2, "description": "reward"}
```

沿用`presents_schema=1`及单调邮件ID。原有四字段行保持不变；类型22另外保存字符串`ItemID`，不把CRC32塞入整型Content。42恒带A4:I、A6:S、A9:I，类型22以外的A6为空串，其余缺省0，所有列长度相同：原生42按本次列集重建邮件表，之后的PPT增量只保留表中已有列，42缺列时新邮件的券池、ItemID和通知分类会丢到下次42。增量PPT仍只在选中行需要时附加这些列。类型22以外的行不能附带额外ItemID，避免固定类型被另一个身份覆盖。新邮件的ItemID须在255字节原生单元内，否则返回503 `present_item_unreplayable`；已保存邮件和物品目录沿用256字节旧上限，继续读取。说明文字的上限为4096字节：客户端A7F380的S单元按256字节读取、显示到255字节，所以更长的说明仅显示截断，没有状态分叉，与原生一致。没有迁移正式存档。

通知分类使用可选`NotificationCategory`，通过`set_notification_category`在父事务提交前装饰已生成的完整邮件。选中行存在显式分类时才追加PPT.A9:I，其他行填0；未分类的旧回包保持原形状。自动通行证补领使用分类7，不改变奖励Type，亦不把原生运行时新到达位写进存档。

`enqueue_groups`支持一次准备多组奖励，在全部通过后统一分配身份和编码，返回每组的实际邮件行；旧`enqueue`复用单组形式。空组保留位置，任一组失败不产生部分状态。扫描包含物品券的邮箱时，在同一只读目录的首尾校验依赖，逐行检查仍保留；不再为每张券重复读取相同静态资源，也不跨请求缓存依赖检查。

## 事务、回包与重试

117按请求顺序逐封累计单位空位、结晶、金币和物品容量。放不下的整封保留，并继续判断后续奖励。固定类型与类型22若指向同一物品，共用一份容量。坏邮件或未知定义直接失败，不当作普通满仓跳过；旧超限持有量不被截断。需要单封领取的邮件（Type16/20券、Type22道具券、恢复品，以及加护、服装和称号等CanAllGet=0的唯一物品）在117中同样跳过并保留，其余邮件照常按序领取；1/2仍要求它们单封领取。117一封也没领到时（空列表或PT2不带PresentID、全是单领邮件、容量全满）回SYSTEM和空PPU，不写回执、不增加修订版，并记录警告。原生6C4020不看117的返回值并随后读42；原生批领列表是否会带上单领邮件仍未证实，跳过属于本地政策。

所有发放、邮件移除、身份高水位与成功回执同次CAS提交。物品信用失败、响应超限或并发重算失败，不会先支付金币或删除邮件。金币回PGP中的A1/A2字符串键值，物品按每个ItemID一行POSSESSION回最终绝对数量，不是奖励差额；POSSESSION恒带Enabled列（未设置的行为0）。原有PPU/PBP和两种PFC形状保持不变。

提交前预检领取包、41及42；金币变化额外预检34，物品变化额外预检129/137。旧成功回执仍保留原字节；只有当前修订版相同才能重放。含PGP、PFC/PPC或POSSESSION的缓存回包分别验证当前余额、资源和读回能力，物品回包还须与当前持有量一致：三列新形状或改动前的两列形状均可，两列形状只在相关行都没有Enabled时成立。不会通过清空回执或重新发奖来修复失效资源。

- 物品目录89项：真实116项、11固定绑定、压缩资源、副作用排除、原生上限、依赖漂移及不可变定义。

- 金币与结晶缓存新增8项：损坏余额、日期和类型不会被成功回执绕过；同时复测3个混合奖励正常重放路径。
- 额外事务及好感/觉醒联动10项：读回容量失败、发放异常、坏邮件、旧调用方及旧奖励生产者。
