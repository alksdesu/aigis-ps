# 官服一键采集

`client/capture-all.ps1` 在一次原版启动中同时采集公共主表、资源版本和官服业务响应，并从响应中导出首份完整的 70/71 召唤调度配对。脚本等待用户从 DMM 手动启动原版，不启动游戏、不点击页面，也不发起抽卡、购买或战斗。

采集器明确支持当前5.0.1原版SHA256 `d0be510fb38b1d6dfe63c3562c97e45f49d318bf7e155dee309d88efe963f92b`，并保留旧版 `babe8210a8652fb25b1c61056ee500b05bd9a3ae37f55d1682a2fb8b850802ba`。陌生指纹仍会拒绝。2026-11-06取得的新主表、资源版本及70/71响应已用于本地数据升级；这不等于私服客户端的原生玩法验收。

## 启动与结束

在项目根目录运行：

```powershell
.\setup.ps1 -IncludeCapture
.\client\capture-all.ps1 -Mode Check
.\client\capture-all.ps1 -Mode Wait -Timeout 7200
```

`Check` 只检查原版文件、指纹与挂点，不附加进程。检查通过后，先正常退出已打开的原版，再运行 `Wait`，从 DMM 启动新的原版进程。两张主表和资源版本在启动期间出现，晚附加可能错过，因此一键入口只提供 `Check`、`Wait`，不提供 `Pid` 模式。

完成本轮准备做的操作后，在采集终端按 Ctrl+C。脚本通知采集器结束、保存已验证的数据并写入汇总；等待它退出后再关闭终端。总时限到期或原版进程退出也会收尾，已经保存的部分结果保留。

## 参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| `-Mode` | `Check` | `Check` 检查，`Wait` 等待新启动的原版并采集 |
| `-Timeout` | `7200` | 总时限，单位秒，范围 1–14400，包含等待原版启动的时间 |
| `-ContentTimeout` | `600` | 主表与资源版本的采集时限，单位秒，范围 1–3600；采集脚本加载完成后计时，并受总剩余时限限制 |
| `-Executable` | `111/aigisr_exe/Aigis_r.exe` | 原版客户端路径；指定路径仍须通过指纹与挂点校验 |
| `-OutputDirectory` | `runtime/capture-runs` | 汇总输出根目录；不改变各采集器的数据目录 |

总时限从等待新原版进程开始计算，附加和加载也不能延长它。某个准备步骤耗时较长、返回时已经到期，脚本不会继续下一次附加或加载。主表和版本采齐或达到自己的时限后，业务响应采集仍可继续，直至本轮结束。

## 采集范围

- `content`：公共 `CardData`、`QuestTable` 和资源版本，沿用 `capture-content.ps1` 的校验与输出格式。
- `responses`：通用响应采集器的 `All` 范围，保留当前排除接口和进程内去凭据规则，详见 [官服响应通用采集](response-capture.md)。
- `schedule`：从同一轮业务响应中提取 70 的 CSS/FPR/SH/GacyaStatus/LCC/PLC 与随后 71 的 CSP，导出首份完整配对，格式与独立调度采集器一致。配对前出现新的 70 时以新一轮为准；70 被拒收时清除旧候选，不能拿旧 70 配新 71。

调度导出仍会单独检查允许的业务组、必需组与结构。合法空组会保留，未收到的组不会补造。只有完整的同轮 70/71 才能作为调度样本；一般响应记录里出现两个注册号，不足以证明配对有效。

## 可以怎样操作

先正常登录，进入主页，打开召唤菜单和商店目录。随后只进行自己本来就计划、且与 [采集与验收清单](../tmp/probe/status/capture-and-acceptance.md) 对应的战斗或页面操作。打开召唤菜单是为了采 70/71，打开商店目录是为了采 46；不需要为了启动采集器而抽卡、购买或消耗资源。

只有实际发生的响应才会被记录。12/13 抽卡和 108 购买样本不会仅因打开菜单而出现；是否执行这些操作由用户另行决定。回归账号、新号、特定活动和 JST 00:00–04:00 等条件仍须分别满足，提供割合页面、断点观察和本地私服的原生验收也不在这个脚本的自动完成范围内。一次启动不能保证 22 条采集与验收任务全部完成。

## 输出与判定

汇总根目录下的本次运行目录包含 `run.json`，`components` 下分别记录 `content`、`responses`、`schedule`。每项有 `path`、`status`、`complete`，遇到错误时另有 `error_code`；尚未产生结果文件时 `path` 为 `null`。应先看各项结果，再读取对应采集器的清单；某一项完整不代表另两项完整。

| 内容 | 默认输出位置 | 检查方法 |
|---|---|---|
| 汇总 | `runtime/capture-runs/capture-*/run.json` | 检查总状态和 `components` 下三个分项 |
| 主表与资源版本 | `runtime/captures/content-*/bundle.json` | `complete=true` 才表示两张主表与版本都齐；读取 `master_manifest`、`resource_context` 定位数据 |
| 通用响应 | `runtime/response-captures/responses-*/` | `manifest.json` 记录结束状态，`records.jsonl` 列出实际采到的注册号与数据 |
| 召唤调度 | `runtime/schedule-captures/schedule-*/` | `manifest.json` 标记完整性，编号 XML 保存通过校验的业务组 |

`responses` 的 `stopped` 表示 `All` 正常停止，不能解释为全部业务都已覆盖。主表未齐、调度未配对或部分响应被拒收时，按各自清单继续补采。`-OutputDirectory` 只改变汇总目录，表中的其他目录不随它迁移，所有输出仍须留在 111 项目内。

| 采集总状态 | 退出码 | 含义 |
|---|---|---|
| `stopped` | `0` | 主表与资源版本完整、首份调度配对完整，且业务响应正常停止并至少保存一条记录 |
| `interrupted` | `130` | 用户按 Ctrl+C，已经开始的采集协作收尾；即使各项数据已齐，仍保留中断状态 |
| `partial` | `1` | 已有部分结果，但未满足上述正常结束条件 |
| `failed` | `1` | 没有可报告的有效采集结果，检查分项错误码或终端错误 |

`Check` 成功时输出 `checked`、退出码为 `0`，不创建采集汇总。等待原版期间按 Ctrl+C，或检查、等待、准备阶段失败时，可能还没有 `run.json`，以终端输出和退出码为准。汇总中的 `coverage_verified` 始终为 `false`；即使总状态是 `stopped`，也不表示业务样本或验收清单已经全部覆盖。

采集结果不会自动导入私服或激活资源版本。主表导入与资源下载仍按 [资源采集清单](collection-plan.md) 执行；这也不能代替原生私服的启动、界面和战斗验收。
