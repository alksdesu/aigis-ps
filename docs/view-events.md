# 演出请求交接

23保存待播放请求、24清除请求已接入，36按原有完整Config响应读回F8。当前原生证据表明：23主要用于表版跳转里版的浏览器交接，固定R18 PC的普通回想不会每次发送它。实现这两个接口不等于所有剧情流程已完成或跨版本跳转已实机验证。

## 原生格式与生命周期

两个操作共享路由`q5ZAHv8g`，分别使用ST3040/3041。业务字段为根F8:S单值。23的当前格式为：

```text
CardId=17,Id=1,Mode=0,Male=0
```

CardId是正int32的事件身份，Id支持当前资源按钮1/2/3，Mode与Male均为0/1。仅允许这四个不同键；字段顺序可变，保存原始字节顺序，不自行改写为另一版本的角色别名。F8所在`EventViewRequest`字段固定256字节，UTF-8正文最多255字节。新请求不是XML、URL或任意脚本。

原生CardId来自发送端rating下的事件别名解析，不是图片别名或实例GetIndex。表版和里版的映射条件不同。回想列表按CardStatus历史生成，可包含已经不持有的角色，因此服务不会用当前名册拒绝此类指针。

24必须显式提交空F8。客户端先读取旧值并解析，再清本地Config、发送24，随后才尝试播放。清除表示交接请求已消费，不表示剧情已播放完毕。后端只持久化指针，不授予观看资格、不修改CardStatus、PEV、好感度或奖励，也不执行其中的内容。复杂剧情资格与播放成功仍由各自业务流程单独处理。

23/24均只回SYSTEM。PGC增量接收器不识别F8，不能通过伪造PGC.F8刷新客户端。21/22的原配置保存白名单保持原样，F8只能走单独的交接接口。服务不会代替客户端打开官方链接。

## 旧存档与重试

原有合法F8完整保留，包括不属于当前四键格式的旧值；24仍可清除这些历史值。只有新23写入使用当前格式验证。初始化不清空旧请求，不补播、不改已读或发奖。

`view_event_history`使用共享RequestLedger（schema2），23/24共享16份回执及最近256个已处理请求摘要，CT不作排序，旧版水位历史读取时自动升级。每个新动作都记录，包括保存相同值或清除已空值，否则旧清除包可能在之后的新保存中再次生效。

同包重试必须匹配当前修订版、状态摘要、配置版本、操作、目标F8和响应。回执已淘汰的已处理请求返回409 `view_event_request_stale`，过期回包返回409 `view_event_retry_stale`，均不重新写入；较旧CT的新请求照常处理。保存与回执在同一次CAS中提交；冲突后可以保留无关配置变化继续，但待播F8本身已被另一操作改变时拒绝覆盖。

24不带目标请求ID或预期版本。第一次到达的旧清除包与合法新清除无法区分，CT也不作排序。该协议仍依赖原生串行调用；未来多客户端乱序写入需要显式协议扩展，不能宣称已有回执解决了这个信息缺失问题。

提交前预检23/24响应和36完整Config。任何验证、编码或提交失败都不会只清请求而丢失其他状态。

控制台`view_event.set`与`view_event.clear`调用与23/24相同的内核`ViewEventService.set_request`/`clear_request`：先核对配置版本，set再按原生四键格式校验请求，然后校验已存Config行，只改F8；经预览、两步提交和审计写入，不写`view_event_history`，提交后客户端在途的23/24精确重放返回409 `view_event_retry_stale`。`view_event.set`的参数为CardId/Id/Mode/Male四个整数，按原生键序拼成F8。两条命令同属view_event组，共用Config.EventViewRequest，字段归属表登记为`view_event.set`。没有待播请求时清除只给警告；清除只表示交接请求作废，不代表剧情进度被清。
